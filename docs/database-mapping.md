# Запись в существующую PostgreSQL

У каждого адаптера может быть `destinations.database`. Настройка определяет подключение, существующие таблицы, ключи обновления и сопоставление колонок. Общий инструмент записи выполняет эти инструкции для любого источника. Он не создаёт и не изменяет таблицы назначения.

Поддерживается PostgreSQL. Другие СУБД требуют отдельного драйвера записи. Это ограничение драйвера, а имена таблиц и колонок настраиваются без изменения программы.

## Подключение и проверка

Секрет подключения находится в настройках сервиса, например в переменной окружения:

```dotenv
ConnectionStrings__Catalog=Host=localhost;Database=existing_catalog;Username=importer;Password=SET_PRIVATE_PASSWORD
```

В адаптере указывается только имя `Catalog`. Служебная БД импортера настраивается отдельно; её таблицы и миграции не нужны в целевой БД.

Перед записью инструмент считывает описание выбранных таблиц и проверяет наличие колонок, обязательные поля, генерируемые значения и уникальные ключи. Просмотр структуры возвращает столбцы и их типы, признак NULL, значения по умолчанию, первичный ключ, уникальные ключи, внешние ключи и индексы. Для обнаружения таблиц подключение должно иметь доступ на чтение соответствующих таблиц.

Один пример адаптера для уже существующих таблиц `media`, `materials` и `media_tags`:

```json
{
  "destinations": {
    "files": { "directory": "/data/media/shikimori" },
    "database": {
      "connection": "Catalog",
      "localUrlTemplate": "https://media.example.test/files/{relativePath}",
      "tables": [
        {
          "name": "card",
          "schema": "public",
          "table": "media",
          "scope": "item",
          "matchColumns": ["source_provider", "source_id"],
          "returning": "id",
          "columns": {
            "source_provider": { "source": "item.provider" },
            "source_id": { "source": "item.externalId" },
            "name": { "source": "item.title" },
            "summary": { "source": "item.description", "onNull": "preserve" },
            "release_year": { "source": "item.year" },
            "updated_at": { "source": "updatedUtc" }
          }
        },
        {
          "name": "screenshots",
          "schema": "public",
          "table": "materials",
          "scope": "assets",
          "role": "screenshot",
          "matchColumns": ["media_id", "role", "position"],
          "replaceScope": {
            "media_id": { "source": "result.card" },
            "role": { "source": "asset.role" }
          },
          "columns": {
            "media_id": { "source": "result.card" },
            "role": { "source": "asset.role" },
            "position": { "source": "asset.position" },
            "url": { "source": "asset.url" }
          }
        },
        {
          "name": "tags",
          "schema": "public",
          "table": "media_tags",
          "scope": "tags",
          "matchColumns": ["media_id", "tag"],
          "replaceScope": {
            "media_id": { "source": "result.card" }
          },
          "columns": {
            "media_id": { "source": "result.card" },
            "tag": { "source": "row.value" }
          }
        }
      ]
    }
  }
}
```

Это фрагмент конфигурации; остальные разделы адаптера (`requests`, `mapping`, `assetPolicies` и другие) остаются обычными. Таблицы должны существовать заранее. В примере `media.id` генерируется самой БД, а пары/тройки из `matchColumns` должны иметь существующие уникальные ограничения или полные уникальные индексы без выражений и условий. Условные уникальные индексы в `matchColumns` не поддерживаются.

`returning` получает фактический ключ записанной или обновлённой строки. Следующие таблицы используют его через `result.card`, где `card` — `name` предыдущей таблицы. Так сохраняется связь с существующим целочисленным или UUID-ключом приложения. Передача ключа из будущего сопоставления запрещена. Возвращаемый ключ доступен только для `scope=item`.

## Источники значений

| Источник | Значение |
| --- | --- |
| `item.title`, `item.description`, `item.provider`, `item.externalId` | Поля нормализованной карточки |
| `item.genres`, `item.tags`, `item.alternativeTitles` | Списки, которые можно записать в JSON или поддерживаемую массивную колонку |
| `item.metadata.someProperty` | Поле исходных дополнительных метаданных; поддержано прохождение вложенных объектов через точку |
| `assets` | Полный список обработанных материалов для записи в JSON/JSONB |
| `asset.role`, `asset.position`, `asset.hash`, `asset.relativePath`, `asset.contentType` | Поля текущего материала при `scope=assets` |
| `asset.url` | Исходный URL для ссылки; для локального файла — `localUrlTemplate` или относительный файловый путь |
| `row.value`, `row.index` | Значение и индекс тега/жанра при `scope=tags` или `scope=genres` |
| `mediaId` | Внутренний ID карточки импортера |
| `updatedUtc` | Время выполнения записи в UTC |
| `result.card` | Ключ, полученный из предыдущего сопоставления `name=card` |

Вместо `source` можно указать JSON-значение `constant`. Одновременно указывать `source` и `constant` нельзя. Шаблон локального URL поддерживает только `{hash}` и `{relativePath}`; реальную выдачу файлов настраивает принимающее приложение. Инструмент записи не публикует HTTP-сервер картинок и не загружает байты изображений в БД.

Имена подключений, таблиц, схем, колонок и логических сопоставлений поддерживают буквы, цифры и подчёркивания и начинаются с буквы или подчёркивания. SQL-фрагменты, пути и выражения в них не принимаются. Значения передаются отдельными SQL-параметрами; произвольные SQL-запросы в JSON не исполняются.

## Пустые значения и коллекции

- `onNull=write` — записать SQL NULL; это значение по умолчанию.
- `onNull=preserve` — исключить пустое поле из записи. При обновлении прежнее значение сохраняется; при создании строки применяется значение по умолчанию самой БД. Если его нет у обязательной колонки, БД отклонит всю транзакцию.
- `onNull=default` — использовать заданное поле `default`, например `{ "source": "item.metadata.summary", "onNull": "default", "default": "Описание отсутствует" }`.

Пустая строка является строкой и не считается NULL. Неверный тип или слишком длинное значение не обрезается автоматически.

Без `replaceScope` коллекция обновляет/добавляет строки по `matchColumns`; отсутствующие в новом ответе строки сохраняются. С `replaceScope` инструмент удаляет только строки, соответствующие всем указанным условиям, и записывает новый набор в той же транзакции. Условия не могут быть пустыми или иметь NULL-значения.

Для замены материалов обязательно задаются `role` и условие роли в `replaceScope` вместе с владельцем. `asset.role` в условиях замены разрешается и при пустой коллекции: оно получает значение `role` сопоставления. При `assetStatus[role]=retry` или отсутствии статуса роли инструмент не меняет её строки. Статус `complete` с пустым набором удаляет строки выбранной роли в указанной области.

Все таблицы одного назначения записываются одной транзакцией. Ошибка проверки ограничения или записи дочерней таблицы откатывает изменения родительской строки и остальных таблиц. Повтор импорта использует те же уникальные ключи и обновляет уже существующие строки.

Поддержаны обычные строковые, логические, целочисленные, десятичные, UUID, даты/время, JSON/JSONB и одномерные массивы text/varchar/int4/int8/uuid. Автоматическая миграция целевых таблиц, произвольные SQL-выражения, запись файлов в `bytea` и автоматическое создание глобального справочника тегов с промежуточной таблицей в этот механизм не входят. Для глобального справочника нужен отдельный заранее описанный способ сопоставления ключей; текущий `scope=tags` предназначен для строк с тегом и владельцем.

## Идентичность, выражения и обновление существующего каталога

`mediaId` в `destinations.database` задаёт правило идентичности целевой карточки. Оно вычисляется общим инструментом записи, без ветвления по имени адаптера. Например:

```json
{
  "mediaId": {
    "coalesce": [
      { "lookup": { "schema": "public", "table": "sources", "column": "media_id", "where": {
        "provider": { "source": "item.provider" }, "source_id": { "source": "item.externalId" }
      }}},
      { "source": "item.externalId", "map": { "41": "old-alias" }, "mapMissing": "null" },
      { "template": "{item.provider}-{item.externalId}" }
    ]
  }
}
```

`lookup` выполняет только параметризованный SELECT выбранной колонки по явно указанным равенствам. Если совпадений больше одного, запись отклоняется как неоднозначная. Для `lookup` требуются права чтения; SQL-фрагменты в JSON не принимаются.

Поддержанные операции над значением:

- `coalesce` — первое значение, отличное от NULL.
- `map` и `mapMissing=original|null` — словарь переименования значений с явным поведением при отсутствии ключа.
- `template` — строка с подстановкой известных источников, например `{mediaId}` или `{item.externalId}`.
- `join` — объединение массива строк; `limit` — явное ограничение длины строки.
- `object` — JSON-объект, каждое поле которого является таким же выражением.
- `merge` — неглубокое объединение JSON-объектов слева направо; позднее значение ключа заменяет раннее.
- `condition` (`left`, `operator=eq|ne|isNull|notNull`, `right`) с `then`/`else` — условный выбор.
- `source=assets`, `role`, `select` — JSON-массив объектов из материалов выбранной роли; `selectValue` даёт массив скалярных значений вместо объектов.
- `first=true` с `source=asset.hash` и `role=poster` — поле первого материала роли, либо NULL при пустом списке.
- `whenRole` — колонка пропускается, если роль отсутствовала или имеет статус `retry`.
- `onUpdate=preserve` — значение применяется при создании строки, но не меняет уже существующее поле. Это позволяет сохранять пользовательское оформление.

Источники также включают `item` (всю нормализованную карточку), `adapterVersion`, `assetStatus`, `warnings`. Контекст версии и эффективных статусов передаётся оркестратором. Пустое выражение или `constant:null` обозначает NULL; пустая строка остаётся строкой.

У таблицы `operation=update` обновляет только найденную строку. Такая таблица не должна повторять все обязательные колонки для INSERT. Стандартное `operation=upsert` создаёт строку при отсутствии и обновляет по `matchColumns`. Перед UPDATE инструмент сравнивает значения: неизменившаяся строка не получает лишний UPDATE и не вызывает соответствующие триггеры.

`role` разрешён и для одиночной таблицы (`scope=item`): при отсутствии роли или `retry` пропускается всё сопоставление. `preserveOnStates:["missing"]` сохраняет существующие данные, если источник вернул недоступный материал. Пустая завершённая роль не считается отсутствующим материалом: она может очистить прежнее значение.

`scope=role` создаёт одну запись для роли, в том числе запись с `state=missing` при завершённом пустом наборе. `scope=files` выбирает только локальные материалы с хешем и относительным путём и удаляет повторения одного файла. `states` дополнительно фильтрует состояния коллекции. Замена коллекции материалов всегда требует отдельной области владельца и роли.

## Предварительный план записи

`PlanAsync` и управляющий API строят план только через чтение. План использует транзакцию PostgreSQL `READ ONLY` и не выполняет INSERT, UPDATE, DELETE, DDL, `nextval`, пробный импорт или откат пробной записи. Поэтому последовательности и триггеры не затрагиваются.

В результате для каждого сопоставления указаны таблица, количества вставок, обновлений, удалений, неизменившихся и неразрешённых строк; для строки — действие, значения ключа и имена изменяемых колонок. Причина пропуска показывает роль `retry`, отсутствие роли или сохранение при `missing`.

Если родительский ID должен генерироваться самой БД, план помечает зависимые строки `unresolved` и ссылается на `result.<alias>`. Он не угадывает будущий ID и не расходует последовательность. Неизвестные серверные значения по умолчанию также помечаются явно. План отражает снимок на момент чтения; конкурирующие изменения, произвольные триггеры и вычисления БД нельзя достоверно предсказать до настоящей записи.

Области `replaceScope` последовательных сопоставлений одной таблицы должны быть непересекающимися, например разные роли материалов одного владельца. Произвольные перекрывающиеся области не моделируются целиком при просмотре плана. В низкоуровневом результате записи `rowsWritten` означает количество обработанных строк, включая неизменившиеся; фактическое отсутствие DML для `noop` проверяется отдельно.

Просмотр структуры использует короткую отдельную read-only транзакцию для каждого отношения. Таблицы и обычные представления удерживаются `ACCESS SHARE`; запросы представлений не выполняются. Для materialized view применяется только `PREPARE` без `EXECUTE`, поскольку PostgreSQL не разрешает `LOCK TABLE` для этого вида отношений ([реализация PostgreSQL](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/commands/lockcmds.c)). Исчезнувшие при конкурентной миграции или временно заблокированные объекты пропускаются с сообщением в `DatabaseSchema.warnings`; после миграции просмотр можно повторить. Это не отключает проверку обязательных таблиц перед записью.
