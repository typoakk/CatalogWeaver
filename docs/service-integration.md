# Подключение к приложению пользователя

CatalogWeaver запускается отдельным сервисом. Для подключения нужны адрес управляющего API и его ключ, настройки источника и решение о хранении результата. Возможны два способа: читать нормализованные карточки через API CatalogWeaver или настроить прямую запись в существующую PostgreSQL приложения. API принимающего приложения для второго способа не нужен.

## 1. Запустить сервис

В Linux используйте последовательность из [README](../README.md): клонировать проект, запустить `docker compose up --build -d` и проверить `/health/ready`. Compose сам создаёт служебные секреты, PostgreSQL, тома настроек и изображений. Установка .NET и PostgreSQL на хост не требуется. Эти служебные таблицы не нужно добавлять в БД приложения. [Подробности запуска и хранения настроек](deployment.md).

Стандартный порт доступен только с хоста. Для управления с другого компьютера можно использовать SSH-туннель к этому хосту или настроенный приватный вход. Передавайте управляющий ключ заголовком `Authorization: Bearer ...`; не помещайте его в URL, адаптер, репозиторий или клиентский браузерный код.

Секреты источников задаются в конфигурации сервиса, например `Importer__Secrets__SteamApiKey`. В JSON источника остаётся ссылка `{{secret:SteamApiKey}}`. Стандартный Compose получает её из `STEAM_API_KEY` приватного `.env`.

## 2. Определить выход

Если приложение будет читать API CatalogWeaver, `destinations.database` можно не задавать. Результаты доступны через `GET /api/v1/importer/items` и `/items/{mediaId}`. Сам сервис продолжает хранить очередь, нормализованные данные и ссылки в своей PostgreSQL.

Для прямой записи укажите именованное подключение. Стандартный Compose передаёт `CATALOG_DATABASE_CONNECTION` из `.env` в `ConnectionStrings__Catalog`. Вне Compose это переменная окружения:

```sh
export ConnectionStrings__Catalog='Host=app-db;Database=existing_catalog;Username=importer;Password=YOUR_PRIVATE_PASSWORD'
```

`localhost` внутри контейнера означает сам контейнер. Подключение должно указывать на адрес БД, доступный именно из контейнера импортера. Для другой Docker-сети настройте общий доступ или сетевой адрес отдельно. Дополнительные подключения объявляются как `ConnectionStrings__ИМЯ` и передаются сервису в Compose.

## 3. Прочитать структуру и сопоставить поля

Получите `GET /api/v1/importer/database/Catalog/schema` либо запустите `dotnet CatalogWeaver.dll --inspect-db Catalog`. Просмотр структуры возвращает таблицы, типы колонок, nullable/default, первичные и уникальные ключи, связи и индексы.

По фактической схеме добавьте в адаптер `destinations.database`. Например, если в приложении уже есть таблица `public.media` с нужными колонками и уникальной парой `source_provider/source_id`:

```json
"destinations": {
  "files": { "directory": "my-source" },
  "database": {
    "connection": "Catalog",
    "localUrlTemplate": "https://media.example.test/files/{relativePath}",
    "tables": [
      {
        "name": "card",
        "schema": "public",
        "table": "media",
        "scope": "item",
        "matchColumns": ["source_provider", "source_id"],
        "returning": "id",
        "columns": {
          "source_provider": { "source": "item.provider" },
          "source_id": { "source": "item.externalId" },
          "name": { "source": "item.title" },
          "summary": { "source": "item.description", "onNull": "preserve" }
        }
      }
    ]
  }
}
```

Это пример фрагмента, а не требование создать именно такие таблицы. Имена, ключи, отношения и поля выбираются под существующую БД. Таблицами и их миграциями управляет приложение пользователя. `--migrate` создаёт только служебную схему CatalogWeaver.

Нужны права чтения метаданных/выбранных таблиц и права записи, соответствующие операциям сопоставления. Для генерируемых ключей могут понадобиться права на последовательности. Ключи `matchColumns` должны соответствовать существующему полному уникальному ограничению или индексу. Подробный пример карточки, материалов и тегов — в [database-mapping.md](database-mapping.md).

## 4. Подключить файлы

`Importer:MediaRoot` задаёт разрешённый корень файлов. В стандартном Compose он равен `/data/media`, связанному с томом `media`. Адаптер указывает относительную вложенную папку через `destinations.files.directory`; выход за корень запрещён.

Чтобы хранить файлы в известном каталоге хоста, замените том `media:/data/media` в своей конфигурации Compose на bind mount, например `/srv/catalogweaver/media:/data/media`. Каталог должен быть доступен пользователю контейнера UID 1654. Исходное изображение скачивается один раз; постоянно хранится выбранный результат или проверенный оригинал при неудаче перекодирования.

Приложение или файловый сервер должны видеть те же файлы. Имя файла — SHA-256 без расширения; фактический MIME-тип есть в данных материала. Раздающий сервер должен учитывать его. `localUrlTemplate` только формирует ссылку для сопоставления: он не поднимает HTTP-сервер и не создаёт маршрут в приложении.

В БД записываются ссылки, пути и метаданные. Файлы непосредственно в BLOB/bytea сейчас не записываются.

## 5. Проверить и начать импорт

1. Проверить JSON через `/adapters/{provider}/validate` и сопоставление через `/database/validate`.
2. Посмотреть `/encoders` и `/image-profiles`; выбрать нужный профиль для каждой локальной роли.
3. Выполнить preview одной карточки с `processImages=true` и `planDatabase=true`. Проверить поля, роли, ссылки, MIME-типы, warnings и план целевой записи. Preview использует реальные запросы источника, но не публикует карточки или файлы.
4. Включить адаптер и импортировать несколько выбранных ID через `/jobs`.
5. Прочитать результат и проверить его со стороны приложения: карточку, отношения, ссылки и доступность файлов. Повторить ID и убедиться, что выбранные ключи не дают дубликатов.
6. Запустить обход с нужным `maximumItems`; полный обход использовать согласно задаче пользователя.

Параметры очереди и лимиты хранятся в собственной БД. Незавершённые задания и страницы обхода продолжаются после перезапуска. Адаптеры и модули перечитываются автоматически; GUI для этого не требуется.

## Обновления и очистка

Роль `retry` сохраняет прежние материалы. `complete` с пустым списком очищает только указанную роль; отсутствующая роль остаётся прежней. Обновление связанных таблиц назначения выполняется одной транзакцией.

Служебная и целевая БД не образуют общую распределённую транзакцию. Перед экспортом файлы закрепляются в служебном состоянии. Старые экспортированные файлы автоматически не освобождаются: сначала нужно установить, что принимающее приложение больше на них не ссылается. Известные свободные файлы очищаются автоматически.

Посторонние незарегистрированные файлы в MediaRoot сохраняются. `Importer:CleanupUnregisteredFiles=true` включает их очистку; применять эту настройку можно к каталогу, которым целиком владеет CatalogWeaver. Не подключайте два независимых служебных состояния к одному корню с такой очисткой.
