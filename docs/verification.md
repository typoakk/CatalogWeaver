# Проверка проекта

## Сборка и тесты

```sh
dotnet build MediaImporter.slnx -c Release
dotnet test tests/MediaImporter.Tests/MediaImporter.Tests.csproj -c Release
```

Для полного прогона задайте `MEDIA_IMPORTER_TEST_CONNECTION` к отдельной PostgreSQL с `test` в имени БД. Проверки создают собственные временные схемы и таблицы, выполняют DML и удаляют тестовые данные. Если переменная отсутствует, проверки БД пропускаются; это не полный интеграционный прогон.

Проверки покрывают JSON-адаптеры, HTTP-лимиты, очередь и аренды, продолжение страниц, нормализацию, обработку изображений, динамические модули, сохранение карточек/файлов, read-only план и универсальное сопоставление с независимой тестовой схемой PostgreSQL. Модели и исходники стороннего приложения для тестов не требуются.

## Docker и первый запуск

```sh
docker build --target checks -t catalogweaver:checks .
docker build --target runtime -t catalogweaver:local .
docker compose up --build -d
docker compose ps
docker compose exec importer curl -fsS http://127.0.0.1:8080/health/ready
```

Образ `checks` содержит тот же тестовый проект для Linux. Для проверок БД передайте ему тестовое подключение и сеть, из которой PostgreSQL доступна. Стадия `runtime` содержит только приложение и runtime-зависимости.

Bootstrap проверяется отдельно: создание секретов без БД, приватные права файлов, повторные/одновременные вызовы, сохранение начальных значений, отказ при конфликте и чтение секретов приложением. Первый Compose-запуск должен работать без `.env`; повторный должен сохранять ключ, пароль и изменения конфигурации.

## Проверка интеграции

Перед реальным импортом прочитайте структуру выбранной БД и проверьте сопоставление. Preview одной карточки с `processImages=true` и `planDatabase=true` должен показать поля, материалы и план без постоянной записи. После ограниченного импорта проверьте карточку и файлы через принимающее приложение. Повтор ID должен обновлять существующую запись по настроенным ключам.

Не используйте рабочую БД приложения как тестовый полигон. Размер реального обхода определяется задачей пользователя. Для проверки конкретной правки достаточно соответствующего сценария; повторять полный внешний каталог не требуется.

Результаты тестов, журналы, дампы и параметры окружения хранятся вне Git. Публичные отчёты содержат только общие условия и результаты, без личных путей, адресов инфраструктуры и секретов.
