# Версии, поставка и обновление

Версия приложения указана в csproj, изменения — в `CHANGELOG.md`. Workflow `release.yml` запускается после публикации тега `vX.Y.Z`: сверяет версию, выполняет полный Linux-прогон с PostgreSQL, собирает образ linux/amd64, публикует его в GHCR и создаёт GitHub Release с digest образа. Код и образ не публикуются этим workflow при обычном push ветки.

Готовый образ появляется только после успешного релизного workflow. Для воспроизводимого запуска выбирайте опубликованный `ghcr.io/typoakk/catalogweaver@sha256:...` из файла digest релиза. Тег версии удобен, но именно digest идентифицирует неизменяемое содержимое. Существующий тег версии workflow не перезаписывает; исправления выпускаются новой версией. Доступность GHCR-пакета настраивается владельцем репозитория отдельно.

## Обновление из исходников

1. Создайте и проверьте резервную копию по `recovery.md`.
2. Прочитайте changelog и изменения контрактов. Для 0.2.0 существующим клиентам нужен `If-Match` при обновлении настроек.
3. Получите выбранный коммит/тег и соберите образ.
4. Остановите прежние worker перед миграцией служебной БД.

```sh
git pull --ff-only
docker compose build
docker compose stop importer
docker compose run --rm migrate
docker compose up -d --wait
```

После запуска проверьте `/health/ready`, `/status`, диагностику адаптеров и один ограниченный импорт на подходящем назначении. Автоматические обновления используют снимки поставленных заданий, поэтому правка шаблона не переписывает прошлые задания. Для осознанного повторного импорта с текущим адаптером используется `/jobs/{id}/retry`.

## Использование готового образа

После публикации релиза выберите его digest:

```sh
export CATALOGWEAVER_IMAGE='ghcr.io/typoakk/catalogweaver@sha256:REPLACE_WITH_PUBLISHED_DIGEST'
docker pull "$CATALOGWEAVER_IMAGE"
docker compose stop importer
docker compose run --rm --no-build migrate
docker compose up --no-build -d --wait
```

Сохраните выбранное значение в приватной `.env` для последующих запусков. Сборка и установка зависимостей на хост не нужны: runtime-зависимости находятся в образе, PostgreSQL поставляется отдельным образом.

## Рабочие конфигурации

Существующие тома `adapters`/`encoders` не перезаписываются при обновлении образа. Поставляемые шаблоны встроены в сборку и доступны через `/templates/adapters/{id}` и `/templates/encoders/{id}` даже тогда, когда том закрывает исходную папку образа. Ответ содержит `shipped`, `currentVersion` и `changedPaths`.

Просмотрите отличия, перенесите нужные исправления в свою конфигурацию, сохраните собственные назначения/политики и проверьте `/validate` и preview. Применяйте через PUT с точным `If-Match` текущей рабочей версии. Само сравнение ничего не записывает; автоматического слияния с риском потерять настройки нет.

## Откат

Замена образа на старый допустима только при совместимой служебной схеме. Старый runtime должен отказаться от несовместимой версии при старте. Автоматического обратного DDL нет. При изменившейся схеме восстановите проверенную копию в новом проекте с сохранённым образом, проверьте назначения и только затем возобновляйте обработку. Согласуйте отдельный откат внешней БД, если приложение требует его.
