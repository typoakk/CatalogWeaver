# Инструкция для агентов CatalogWeaver

## Назначение и границы проекта

CatalogWeaver — самостоятельный headless-сервис .NET 10 для импорта медиакаталогов. Целевой запуск — Linux / Docker Compose. Windows поддерживается для разработки и запуска .NET. GUI отсутствует; управляющий REST API служит основой будущего интерфейса.

Начни с [README](README.md), [текущей схемы](docs/architecture.puml), [маршрутов API](docs/api.md) и [подключения приложения пользователя](docs/service-integration.md). Для работы с назначением прочитай [database-mapping.md](docs/database-mapping.md); для изображений — [encoders.md](docs/encoders.md).

Новые источники описаны в [adapters.md](docs/adapters.md), все настройки — в [settings.md](docs/settings.md). Перед обновлением/восстановлением прочитай [recovery.md](docs/recovery.md) и [releases.md](docs/releases.md). Фактические контракты доступны через авторизованный `/openapi.json` и JSON Schema в `schemas/`.

Изменяй только этот репозиторий и согласованное окружение проверки. Конфигурации конкретных приложений находятся вне этого проекта. Здесь остаются универсальные примеры в `examples` и проверки на независимых тестовых схемах. Не переноси правила конкретного приложения в общий оркестратор.

## Архитектура, которую нужно сохранять

- Один общий оркестратор и инструменты; поведение источника описывается адаптером. Новому источнику не нужен отдельный worker или специальный writer.
- Служебная PostgreSQL отделена от необязательной PostgreSQL приложения. Таблицами назначения и их миграциями управляет приложение пользователя. Не добавляй DDL цели в `--migrate`.
- `destinations.database` задаёт имя подключения, таблицы, колонки и ключи. Значения параметризуются, идентификаторы проверяются. Не добавляй пользовательский raw SQL.
- HTTP источника, CDN, preview и discovery используют общий лимитер. Сохраняй `allowedHosts`, запрет непроверенных перенаправлений и приватность секретов.
- Адаптеры и модули автоматически перечитываются. Неверная правка не уничтожает рабочую версию; ошибка должна быть видна в API. Удаление модуля и коллизии описаны в `docs/encoders.md`.
- Снимок задания фиксирует JSON и его хеш, в том числе `resolvedImageProfile`. Обычное сохранение адаптера разрешает профиль заново; выполнение очереди использует сохранённые инструкции. Старые JSON и их исходные хеши должны оставаться читаемыми.
- Не записывай вручную вычисленный `resolvedImageProfile` в исходный шаблон адаптера. Это служебная часть канонического снимка; профиль выбирается через `imageProfile`.
- Оригинал скачивается один раз. Для всех форматов общий порядок: проверка кандидата, повторная проверка, повторное перекодирование оригинала, до двух проверок нового кандидата, затем проверенный оригинал при неудаче. Больший корректный результат принимается.
- Сохраняй размеры после ориентации и точную прозрачность. Не удаляй альфа-канал ради JPEG. Анимация и глубина более 8 бит остаются в оригинале текущего Q8-runtime.
- Ссылки на выбранный файл фиксируются до удаления оригинала из staging. Сохраняй leases, fences и защиту от очистки активных/экспортированных файлов.
- Preview не публикует постоянные файлы и карточки. План назначения не делает пробных DML-записей или расходования последовательностей. Реальные HTTP-запросы preview продолжают расходовать лимит.
- Публикация идёт через `IImportPersistence.PublishAsync`: намерение фиксируется до изменения диска; прямой вызов ImagePipeline для реального импорта обходит восстановление. Очистка учитывает leases, активные публикации и экспортные резервы.
- `FieldStatus` различает успешное пустое значение и сбой получения. Недоступные/неописанные поля не перезаписывают прежнее значение или актуальное поле внешней БД. Снимки без новых флагов остаются читаемыми.
- Нативные операции выполняются через `ProcessImageCodec` в ограниченных дочерних процессах. При отмене сначала дождись прекращения процесса, затем удаляй staging. Не заменяй это обычным WaitAsync над неотменяемой функцией.
- Существующие конфигурации API изменяются с точным ETag в If-Match. Сравнение шаблонов не применяет изменения. Старые зафиксированные задания не нужно переопределять при усилении проверки новых конфигураций.
- Не удаляй экспортные резервы по возрасту. Освобождение требует рассмотренной ревизии и явного подтверждения проверки внешних ссылок; сам файл запрос освобождения не удаляет.

## Как подключить сервис пользователя

1. Установи, где запускается CatalogWeaver, откуда получает данные, где хранит изображения и как приложение читает результат. При наличии конфигурации сначала изучи её; не выдумывай адреса и схему БД.
2. Запусти выделенный сервис по Linux-инструкции README. Обязательного `.env` нет: Compose выполняет bootstrap секретов, запускает PostgreSQL, миграции и worker. Проверь `/health/ready`, авторизацию и диагностику адаптеров/модулей. Подробности в `docs/deployment.md`.
3. Если нужен прямой экспорт, добавь приватное именованное подключение `ConnectionStrings__NAME`; в Compose явно передай его сервису. Служебная `ImporterDb` остаётся отдельной.
4. Прочитай фактическую структуру через `/database/NAME/schema` или `--inspect-db NAME`. Сопоставь существующие поля, ключи и связи в `destinations.database`; проверь конфигурацию API. Не создавай лишние таблицы ради шаблона.
5. Настрой `Importer:MediaRoot` и вложенную папку адаптера. Организуй доступ приложения/файлового сервера к тем же файлам и корректному MIME-типу. `localUrlTemplate` только формирует URL и не создаёт сервер изображений.
6. Получи `/image-profiles` и выбери профиль в `assetPolicies`. Для нового профиля добавь модуль по `docs/encoders.md`, дождись сканирования либо вызови `/encoders/reload`.
7. Выполни preview с обработкой изображений и планом БД. Затем проверь небольшой реальный импорт, чтение результата приложением, доступность файлов и повтор ID без дубликатов. Размер последующего обхода определи по задаче пользователя.

Подробности и примеры находятся в `docs/service-integration.md`. Если приложение не использует PostgreSQL, его можно подключить к нормализованному API; текущий прямой writer для другой СУБД потребуется реализовать отдельно. Запись файлов в BLOB/bytea не реализована.

## Проверка изменений

Перед работой проверь ветку и незакоммиченные изменения; используй ветки `codex/`. Не перезаписывай изменения пользователя. Не изменяй другие проекты и работающие сервисы ради проверки этого репозитория.

Сборка: `dotnet build MediaImporter.slnx -c Release`. Тесты: `dotnet test tests/MediaImporter.Tests/MediaImporter.Tests.csproj -c Release`. Для полного прогона задай `MEDIA_IMPORTER_TEST_CONNECTION` к отдельной тестовой PostgreSQL с `test` в имени. Без неё часть тестов пропускается; не сообщай такой прогон как полный.

При изменении кодировщиков проверь реальные native encode/decode, MIME, прозрачность, ориентацию, fallback, загрузку нового модуля и неизменность снимка очереди. При изменении writer проверь план без записи, повтор без дубликатов, связи и транзакции. Docker target `checks` проверяет тот же код в Linux. CI запускается на push и pull request.

Секреты находятся только в приватном окружении или томе `configuration`. Bootstrap создаёт их один раз и сохраняет при повторных запусках; файлы доступны владельцу, в журналы значения не выводятся. `.env`, `.local`, дампы, результаты тестов и сборки исключены из Git; `.env.example` содержит только пустые поля и общие настройки. Не печатай ключи/пароли и не копируй реальные строки подключения, личные пути или адреса окружения в документацию, логи, тесты или коммиты. Перед публикацией проверь `git diff --check`, состав diff и отслеживаемые файлы. Вместе с поведением обновляй актуальные документы; исторические отчёты явно оставляй историческими.
